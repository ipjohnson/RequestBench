§1 · The gap

A number with no link to its code

Every published ratio is produced by a specific version of a specific file, and nothing in the record says which.

A run writes an env row and one target row per target. The target row carries framework, version, runtime, adapter and serializer — everything about the dependency, nothing about the code that calls it. The run id ends in six hex characters that look like a content hash and are not: harness/run.py:398 is uuid.uuid4().hex[:6], a nonce to keep two runs in the same minute from colliding.

So when a target's ratio steps between two nights, the first question — did the wiring change, or did the machine? — cannot be answered from the record. It has to be reconstructed by hand from git log, and only if someone remembers to look.

docs/plan.html already specifies the fix and it was never built. Its invalidation table lists framework app source against re-measure that one target, both suites, with the mechanism given as content hash. This document is that row, plus the two things it turns out to need: the file set has to be defined before it can be hashed, and the thing worth showing a reader is not a hash.

§2 · The bundle

Code, prose, and the manifest that resolved it

A bundle is every file that decides how a target behaves, plus the prose that explains it.

Bundles are small. Fastify is one file of wiring; Gin is one; Spring Boot is two plus a POM. The shared domain is three more, and it belongs in every Node target's bundle because a change there moves all six at once.

RoleWhat it holdsExampleFiles
sourceThe target's own wiring. The only thing that differs between frameworks in a language.targets/node/fastify/app.js1–3
sharedThe domain module every target in the language calls. Changing it moves every target at once, which is why it is in each of their bundles.targets/node/_shared/domain.js1–3
manifestThe dependency declaration the version was resolved from.targets/node/package.json1–2
configFramework configuration that is not code. Where a feature is often turned on.…/micronaut/src/main/resources/application.properties0–2
hostThe entry point for an execution host, where the target has a separate one.targets/java/spring-boot/…/rb/lambda/Handler.java0–3
proseNew. Hand-written. What this framework is, how it is wired here, and what is unusual about it.targets/node/fastify/README.md1

The prose is the part that does not exist yet and is the reason to build any of this. A reader who opens Fastify wants to know what they are looking at before they read a route table: that it compiles a JSON Schema per route and that this benchmark deliberately bypasses that by handing req.body to the shared validator, that its content-type parser is overridden here so a function host can hand it a pre-parsed body, that @fastify/compress is registered non-globally so the rest of the blend is unaffected. None of that is recoverable from the code, and all of it is the answer to "why is this row where it is."

One README per target, roughly a screen of text, reviewed in a diff like everything else. It sits in the bundle, so it is hashed and versioned with the code it describes.

§3 · Determinism

The hash has to be reproducible or it is worse than nothing

A hash that shifts for reasons unrelated to the code would report changes that did not happen, and the first false alarm retires the whole mechanism.

Five rules, versioned together as bundle-v1, because changing any of them silently reissues every hash in the series.

RuleWhy this way
File set comes from git ls-files over the bundle's roots, never a filesystem walkA walk picks up whatever is on disk: an editor backup, .DS_Store, a stale build artifact, node_modules. Git's index is the definition of what is committed, and it is identical on every machine that checks out the same commit.
Paths repo-relative, forward slashes, sorted bytewiseDirectory order differs between filesystems, and locale-aware sorting differs between machines. Bytewise on a normalised path is the same everywhere.
SHA-256 over raw file bytes, hex, full digestNo truncation: these are per-file identities in a series kept for years, and the manifest is small enough that sixty-four characters cost nothing.
.gitattributes pins * text=auto eol=lfWithout it a Windows checkout produces CRLF, every file hash changes, and every target looks rewritten. This is the failure mode most likely to actually happen.
Bundle hash is SHA-256 over the canonical manifest text, one <hash>  <path> line per file in sorted orderHashing a JSON serialisation would make the hash depend on key order, spacing and how a language's encoder escapes. A line-oriented canonical form has one representation.

Two rollups, not one

Per-file hashes mean any subset can be rolled up after the fact, and two subsets are worth naming. code_hash covers source, shared, manifest, config and host. bundle_hash covers those and prose.

Regression attribution uses code_hash, so that correcting a typo in a README does not read as a target that changed. Page rendering uses bundle_hash, so that a corrected README does produce a new page. Keeping both is free once the manifest lists files individually, and conflating them would make one of the two behaviours wrong.

§4 · The manifest

What a run writes down

One manifest per target per run, content-addressed so an unchanged target writes nothing new.

{
  "bundle_version": "bundle-v1",
  "target":     "node:fastify",
  "bundle_hash": "sha256:9f2c…",        every file, prose included
  "code_hash":   "sha256:41ab…",        every file except prose
  "commit":     "3c545cd…",
  "framework":  { "name": "fastify", "version": "5.12.4", "license": "MIT",
                  "repo": "https://github.com/fastify/fastify",
                  "homepage": "https://fastify.dev/" },
  "files": [
    { "path": "targets/node/_shared/domain.js", "role": "shared",   "bytes": 9316, "hash": "sha256:…" },
    { "path": "targets/node/_shared/host.js",   "role": "shared",   "bytes":  742, "hash": "sha256:…" },
    { "path": "targets/node/fastify/README.md", "role": "prose",    "bytes": 1840, "hash": "sha256:…" },
    { "path": "targets/node/fastify/app.js",    "role": "source",   "bytes": 4108, "hash": "sha256:…" },
    { "path": "targets/node/package.json",      "role": "manifest", "bytes":  711, "hash": "sha256:…" }
  ]
}

The run record gains three fields and nothing else: bundle_hash and code_hash on each target row, beside serializer, and commit plus repo on the env row. That is about ninety values for a forty-three target run, well under a kilobyte, and it is what makes every past run answerable.

repo is the owner/name slug, taken from GITHUB_REPOSITORY when a run is in Actions and parsed from git remote get-url origin otherwise. It is recorded rather than hard-coded so a fork's pages link to the fork's own code, and it is what turns the manifest into something clickable — see §7.

Manifests themselves are written once per distinct bundle_hash, not once per run. A manifest is five to ten file entries, roughly a kilobyte; a full set across forty-three targets is about forty kilobytes, and a night where nobody edited a target adds nothing at all. That is the same content-addressing argument as the quantile summaries in docs/blend-v2.html: nightly cost should track how often things change, not how often they are measured.

Where the content itself comes from

The manifest holds hashes, not file contents. The site build runs inside the repository and therefore has the full history, so it resolves each path with git show <commit>:<path> and checks what comes back against the recorded hash. Storing contents as well would duplicate git for no gain.

This has one real failure mode and it should behave loudly. If history no longer holds a path — the file was moved, or the branch was rewritten — the hash will not verify, and the page says the source for that run is unavailable rather than rendering today's file under an old number. Silently showing the wrong code is the thing this whole design exists to prevent, so the check is not optional.

§5 · Framework metadata

Derived at run time, not declared by hand

Repository, licence and homepage are already sitting in the resolved dependency tree at the moment a run boots.

LanguageSourceYields
nodenode_modules/<pkg>/package.jsonversion, license, homepage, repository. Present after the npm ci the run already does.
gogo.mod module pathThe repository directly: github.com/gin-gonic/gin is both the import path and the repo. Licence from the module cache.
javathe resolved POM in the local Maven repository<url>, <scm> and <licenses>, after the build Maven has already run.

Deriving beats declaring here for the same reason the framework version is already derived rather than written into matrix.json: a declared repository URL is correct until the day it is not, and nothing would notice. It also means a framework that moves its repository is reported correctly the next night with no pull request.

What stays declared in spec/matrix.json is the thing no manifest knows: which mechanism each target used for each feature, and why a target has none. That declaration is mechanisms, one entry per target per family, and it is what makes a missing feature mark fail: a family that names a mechanism has to produce at least one wiring part, and a family with nothing to show says so in a sentence the page renders instead.

§6 · The framework page

What a reader gets when they click a row

A short README rather than a code dump. The full source is a link; the page is the orientation.

Identity
The project's logo, then Fastify 5.12.4 · node 24 · MIT · repository, homepage and docs, from the manifest. The version is the one that was measured, not the one on npm today.
Prose
The hand-written README. What this framework is, how it is wired here, what is unusual. The only part a person writes.
Standing
Its current ratio, its rank within its language, and its own history. Links back to the table it came from.
Handlers
Three snippets, chosen rather than arbitrary: json.small for the plainest possible route, parameters.two for captures, and one feature wiring. Defaulted, overridable per target where the default is unrepresentative. Each one links out to those exact lines on GitHub at the commit that was measured, so reading further is one click rather than a search.
Features
One row per feature family: the declared mechanism, the dependency that provides it, and the configuration snippet. This is where @fastify/compress, route-scoped sits next to Spring's server.compression.enabled.
Bundle
The file list with per-file hashes, and which files changed since the previous run. Usually empty, which is the point: when it is not, it is the first thing to read.

Logos

The mark is what makes a row recognisable before the name is read, and it is the one asset on the page that cannot be derived: no package manifest carries a logo field. Four decisions make forty-three of them tractable.

DecisionWhy
Vendored into site/logos/, never hot-linkedA hot-linked mark breaks when a project reorganises its site, and it points every visitor's browser at someone else's server. Vendoring also means the page renders offline and from a build artifact.
Recorded in site/logos/index.json: source URL, licence or brand-guideline URL, the date fetched, and whether redistribution is permittedUsing a mark to identify the thing being benchmarked is ordinary nominative use, which is what every comparison does. Some projects still publish brand terms that restrict redistribution, and a few have none at all. Recording the answer per logo takes one line and makes the question answerable later without re-deriving it.
Normalised to a fixed box on a neutral tile, SVG preferredForty-three marks arrive at every aspect ratio, some square glyphs, some wide wordmarks. A fixed box with padding makes a grid of them read as one system. The tile matters more than it sounds: plenty of logos are dark-on-transparent and disappear entirely on a dark ground, and a fixed tile background guarantees contrast in both themes without needing a second variant of every mark.
A monogram fallback, rendered from the framework name in the page's own typeSome targets have no logo — chi and gorilla/mux are libraries rather than products with a mark. Others have terms that do not permit vendoring. A typographic fallback covers both without leaving a hole in the grid, and it is a deliberate placeholder rather than a broken image.

Logos stay out of the bundle, for the same reason prose stays out of code_hash. A logo is a property of the framework, not of the target's wiring, and swapping one should not read as a target that changed. They live under site/ with the rest of the presentation, and the gate checks only that every target resolves either a vendored mark or a declared fallback reason.

Comparison, which is the other half

The same data transposed gives the two views worth having. An endpoint page stacks every target's wiring for one endpoint, grouped by language — because the domain logic is shared, what remains is only the wiring, so three lines of Fastify sit legibly beside three lines of Gin and a Spring annotation. A feature page does it for a mechanism rather than a route: for each target, the declared mechanism, the dependency line, the configuration, and the route it is scoped to.

The feature page is the one that explains the numbers. A reader looking at the compression column can see that one target buffers the whole response and another streams it, stated as code rather than inferred from a bar.

§7 · Extraction

Snippets come from the path, not from markers

Measured against the nineteen implemented targets rather than assumed.

An endpoint's wiring can be found by matching its spec path as a regex that tolerates any capture syntax — :one, {one}, <one> — then expanding from that line backward through annotations and forward to balanced delimiters. Run against all nineteen targets, every framework target resolves 38 of 40 endpoints. The two it misses are the same two everywhere and they are correct misses: one is a value on a route that already exists, the other is deliberately unregistered. Annotations and route tables both work, across sixteen frameworks in three languages.

The baselines resolved 4 of 40, and that was the finding that ended them. They dispatched with a segment switch — switch (seg[0]) { case "plaintext": … } — so there was no path literal anywhere to anchor on, and a marker inside such a switch captures a condition rather than a handler. They have since been removed; every remaining target registers routes with the path written down, which is what makes derivation work at all.

CaseCoverageTreatment
16 framework targets38 / 40Derived. No annotation.
Feature configuration—Markers. There is no path to anchor on, and the configuration is often in another file entirely.
Routeless endpoints2A spec field, not a marker: errors.not_found points at domain.lookup's route, errors.unmatched at the framework's 404 handler.

Two checks keep an extraction honest. Every snippet must contain the path it claims to implement, which catches a wrong expansion instead of shipping it. And a path that matches in more than one place is an error rather than a first-match, because the prototype's first-match rule is exactly how a comment or a test would get rendered as the implementation.

Both of those ask where a snippet is. Neither asks what is in it, and a bare @Get("/json/small") passes both while showing a reader nothing: 403 of the published snippets were exactly that. spec/marks.json holds the assertions that ask the second question — a snippet may not be nothing but annotations, and a handler with its support has to reach the shared domain — against a committed allowance that only ever goes down. Those two are clear across the whole corpus. The allowance carried coverage after that, which Target Suites §5 explains, and it is empty now.

Both of those are still about a handler. A third thing a page is right about is whether the endpoint is tested at all, and with what. rb:test now carries required: "ratchet", a value that means neither every nor never: the endpoints with no test are counted against the allowance rather than gated red, because every drops the record and would empty the snippet map for all 1,650. Every one of the 1,650 has a test today. Its assertion is reads_expectation, which asks that a test snippet name the endpoint it is marked for, since that is the key spec/expected.json is read by and a literal status or body in a test is how 1,650 assertions drift away from the file that decides what a correct answer is. Beside it, and a requirement rather than an assertion, spec/matrix.json gains suites: a family with a marked test declares the facility it tests with and whether that runs in the process or over a socket, per family rather than per target, because a target that tests in-process everywhere except compressed is the case a per-target flag would hide.

Marks are typed, and the kinds live in the spec

A mark is rb:<kind> <selector>[,<selector>…], closed by rb:end where the block rule would stop short of what the author meant. A selector is family.endpoint for one, family.* for all of a family, or * for the target. spec/marks.json says what each kind selects, which file roles it may read, and what has to be true of what it captured, so harness/snippets.py never learns a kind's name and adding one is an object in the spec and a display section.

A route defined in an API description is derived from it like any other. A file named openapi.yaml, openapi.yml or openapi.json in a target's directory is role contract rather than config: it says what the target serves, so it is in code_hash and in reach of derivation, while a .yaml holding settings is neither. A target that still registers the route in code as well has it in two places, which is the §7 ambiguity error and not a first match.

That is a rule about a target that routes from a description, and it makes the opposite case a trap. A description written out of the routes is the same file name saying the same thing twice, so dropping one into any of the thirty-three targets turns all fifty of its endpoints ambiguous at once. harness/bundle.py catches /client/ and /suite/ ahead of the name rules for that reason: a generated client and its description are held to the target rather than served by it, which is role test.

Three kinds are declared and two carry the work. rb:handler names the lines that answer the request, and derivation stays the way in wherever the route literal sits on the declaration: 1,097 of the 1,650 are still located without a mark. rb:wiring names the code that makes a feature family work and that the route does not mention — the gzip express mounts three statements above a route that says nothing about compression — keyed by family, because six compressed.* endpoints share one set of parts. rb:test is the third, and adding it was the test of whether any of this is extensible: one object in the spec, a test role in bundle.py that goes into bundle_hash but not code_hash exactly as prose already does, and one display section. No change to mark parsing and none to the gate. It had nothing to mark for a while; targets/*/*/suite/ is what it marks now, at the same role and for the same reason.

Every snippet is a link into GitHub

The expansion already computes where a snippet starts and ends, so recording those two numbers costs nothing and makes each snippet addressable in the browser. A snippet record is the path, the line range, and the hash of the file it came from.

{ "endpoint": "json.small", "target": "node:fastify",
  "path": "targets/node/fastify/app.js", "start_line": 30, "end_line": 30,
  "hash": "sha256:…" }          the file's hash, from the bundle manifest

composed at render time from env.repo + env.commit + the record above:
https://github.com/ipjohnson/RequestBench/blob/853ae6c…/targets/node/fastify/app.js#L30

Four rules about that URL. It is composed at render time rather than stored, because the parts are data and the template is presentation; storing full URLs would bloat every record and hard-code the host. It always uses the full forty-character SHA rather than a branch name, so a link from a run in March still opens the code that ran in March. It uses blob rather than raw, so the reader gets highlighting and the range highlighted in place, and can browse outward from there. And a single-line snippet emits #L30 rather than #L30-L30, which is what GitHub's own copy-link produces.

The link is emitted only when the file's recorded hash verifies against the content at that commit. A mismatch means the line numbers describe different bytes than the ones measured, so the link would open real code at the wrong lines — the most convincing way to be wrong. The page shows the snippet without a link in that case and says why.

One practical limit: a permalink to a commit that was never pushed returns a 404. Nightly runs are Actions runs on a pushed commit, so this only affects local runs, and a local run is already marked a smoke test and never recorded. Where the commit is not on a remote, the page renders the snippet and omits the link rather than guessing at a branch.

§8 · Machinery

What this adds

FileChange
.gitattributesNew. * text=auto eol=lf. Without it the hashes are not reproducible across checkouts, which makes everything else here unreliable.
harness/bundle.pyNew. Resolves a target's roots to a file list through git ls-files, hashes each file, derives the framework metadata from the resolved dependency tree, and emits the manifest. Called by run.py per target and standalone for the site build. bundle-v2 brought the conformance client's contract into the file set at role test, which moved every bundle_hash and no code_hash.
harness/run.pyWrite bundle_hash and code_hash on each target row and commit plus repo on the env row. This is the only change that has to land before the next run to be worth anything, because it is the only one that cannot be backfilled.
harness/snippets.pyNew. Derives endpoint wiring from spec paths, reads typed marks for what no path can reach, records each part's line range, and enforces the checks in §7.
spec/marks.jsonNew. The mark kinds, what each may read and claim, the assertions a captured snippet has to pass, and the allowance recording how much of the corpus still fails them.
spec/matrix.jsonBundle roots per target, where the convention does not cover it, and mechanisms: one declaration per target per family, naming the framework facility and the dependency behind it, or saying in a sentence why there is nothing to show.
targets/<lang>/<target>/README.mdNew, one per target. Nineteen to write now, forty-three eventually. The largest piece of work here and the only part that is not mechanical.
site/logos/New. One normalised mark per target plus index.json recording each one's source, terms and fetch date. Outside the bundle on purpose.
site/Framework pages, endpoint comparison pages, feature comparison pages, rendered by site/src/pages/f/[slug].astro. harness/siteview.py resolves file content from git at the recorded commit and the page verifies it against the manifest. Renders the monogram fallback where no mark is vendored.
.github/workflows/validate.ymlCoverage gate, the same shape as the conformance matrix: every target resolves a snippet for every endpoint it implements, every snippet contains its own path and passes the assertions, every family declares a mechanism and produces the wiring it named, every declared feature dependency exists in that target's manifest, and every target has a README.

One ordering constraint

Everything here except the run-record fields can be built later and applied to the code as it stands. bundle_hash, code_hash and commit cannot: a run that did not record them cannot have them added afterwards, because the point of the record is what was true at the moment it was measured. Every night that passes without them is a night whose numbers stay unattributable.

§9 · Sequence

Order of work

  1. .gitattributes, then bundle.py, then the run fields

    The line-ending pin has to precede the first hash or the first cross-platform checkout invalidates everything. These three are small and they are the only time-sensitive part.

  2. The snippet extractor and its gate

    Derivation wherever the route is a literal, markers for routes registered from a loop or a group and for handlers with no route at all. The gate goes in at the same time, because an extractor without coverage enforcement quietly stops covering things.

  3. Feature markers and the mechanism declarations

    Follows the feature families in docs/blend-v2.html landing in the targets. Marking a registration that does not exist yet is not possible.

  4. The READMEs

    Nineteen of them. Worth writing as each target is touched for the blend-v2 wiring rather than as a batch afterwards, because that is when the unusual parts are fresh.

  5. Framework pages, then the comparison views

    The single-target page first, since it needs only one manifest and one README to be worth looking at. Logos can be collected in one pass at any point, since nothing depends on them. Endpoint and feature comparison pages come free from the same data once more than one target is done.
