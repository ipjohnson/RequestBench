Framework Benchmark Rotation

Thirty-seven web frameworks across six languages, measured on local emulators rather than cloud accounts. Each language runs on its own night, alternating between a throughput blend and a capability sweep that covers middleware, auth, templating, compression, static files, SSE and WebSockets.

§1

Why emulators, and what the numbers mean

The constraint is account signup, automation, and IAM, not cost.

Everything measured here lives inside the framework process: routing, body parsing, middleware dispatch, serialization, template rendering, compression, connection handling, and JIT behaviour under mixed load. That is the whole subject of the benchmark, and an emulator reproduces it exactly, because the code under test is the same code.

What the emulator cannot give you is anything owned by the platform: microVM boot, code download, SnapStart restore, container scheduling, concurrency throttling, and the latency of managed services. None of that is in scope, and no number in this report should be read as a claim about it.

The distinction that matters when picking tools. Some emulators are the production code path. The GCP Functions Framework is the same library that runs in Cloud Run. Azure Functions Core Tools starts the real WebJobs host. The Lambda Runtime Interface Emulator speaks the real Runtime API.

LocalStack, Azurite, and the Firestore emulator are independent reimplementations. They are correctness tools. Keep them out of the measured path entirely.

§2

The matrix

Six frameworks per language, seven for .NET, plus a bare baseline that never changes.

The baseline is the last row of every shard and the most important target in it. It is the same runtime, the same harness, the same load generator, serving the same routes with no framework in the path. Every framework is reported as a ratio to it, which is both the fair comparison and the number you actually want.

Warmup is a property of the runtime, not the framework, which is the main reason language is the right sharding axis. A JVM needs C2 to settle and .NET needs tiered compilation to finish. Go, Rust, Node, and Python are at steady state in seconds. Sharding by language also means one toolchain cache and one pinned runtime version per shard.

§3

Two kinds of night

A throughput night ranks. A capability night explains.

SSE, WebSockets and compression do not fit a request-rate ladder, and templates and static files would swamp a blended aggregate with their own response sizes. So the workload splits in two. The throughput night runs the 40-endpoint blend as a rate ladder and produces the ranking. The capability night runs ten short suites against one long-lived process and produces deltas, not rankings.

The throughput ladder

Spend the 300 seconds as five 60-second rungs at ascending offered rate rather than one flat window. A single rate tells you almost nothing: too low and every framework looks identical, too high and you are measuring queue depth. The ladder gives you the latency curve and the point where it knees.

Rungs are fixed in absolute terms and shared by every target in the shard, so all frameworks are compared at identical offered load. A framework that cannot hold the top rung shows it as queueing, and that is the result, not a reason to retune the rung.

RungOffered rateDurationRequestsPurpose

512 000 rps60 s720 kSaturation behaviour

Open loop, always. Use wrk2, vegeta, or k6 with a constant arrival rate. Closed-loop tools such as ab and plain wrk suffer coordinated omission, and every tail number they report becomes fiction the moment a framework starts queueing. Pin the generator to different cores than the target with taskset, and set the governor to performance.

§4

Fourteen nights, alternating

Throughput one week, capabilities the next. 14 h 48 m of work, no night over 92 minutes.

Why alternate rather than lengthen

Running both suites every night would put .NET at over two and a half hours and leave no slack for a retry. Capability performance also moves far more slowly than core dispatch performance: a framework's compression or template path changes on a release boundary, not on a commit. A fortnightly cadence matches how fast the answer actually changes.

The cost is that a capability regression can sit undetected for two weeks. That is the right trade as long as the throughput blend still runs weekly, because a regression large enough to matter usually shows up in the blend first.

# .github/workflows/shard.yml — one file, fourteen nights
on:
  schedule:
    - cron: '0 2 * * 1'   # Mon — java    (suite from ISO week parity)
    - cron: '0 2 * * 2'   # Tue — go
    - cron: '0 2 * * 3'   # Wed — node
    - cron: '0 2 * * 4'   # Thu — python
    - cron: '0 2 * * 5'   # Fri — dotnet
    - cron: '0 2 * * 6'   # Sat — rust
    - cron: '0 2 * * 0'   # Sun — anchor

concurrency:
  group: bench-host-${{ runner.name }}   # one measurement at a time, ever
  cancel-in-progress: false

Builds are the part that fans out. A build is deterministic given its lockfile, so it is content-addressed, cacheable, and can run anywhere at any width. Run all 43 builds in parallel on hosted runners hours before the window opens, push the images, and let the measurement job pull by digest. Only measurement needs the dedicated host, and measurement is the only thing the concurrency group protects.

§5

Two barometers, different jobs

One normalizes. One decides whether the night's data is admissible.

Bare baseline — the normalizer

Written in the shard's own language and run inside the shard alongside every framework. Raw net/http, bare Netty, node:http, raw ASGI, a plain Kestrel RequestDelegate, hyper.

Every framework is published as a ratio to this. It divides out both machine speed and how that runtime behaved on that machine tonight, and what remains is framework overhead.

Machine calibrator — the admissibility check

One fixed native binary, byte-identical in every shard, doing an HTTP round trip with some JSON and some allocation. Run it at the start and end of every night.

If the two readings disagree by more than 3%, the host drifted mid-run and the shard is quarantined rather than published. Do not divide it out: machine speed does not affect CPU-bound and memory-bound work proportionally.

Pin both forever and treat a change to either as a schema migration. If a barometer has to change it becomes v2, both versions run through a transition window, and every stored result records which one produced it. The day you quietly improve a barometer is the day the history stops meaning anything.

§6

Suite A — the throughput blend

One stream over 40 endpoints, tagged per request, weighted by a fixed vector.

All 40 endpoints are live in a single stream for the whole 300 seconds. That is the realistic condition and the one worth ranking on: with 40 handlers hot, shared call sites in the router and the serializer go megamorphic, the instruction cache is under real pressure, and the allocation size distribution looks like production. An isolated single-endpoint run hands the JIT a monomorphic hot loop, which flatters every framework and flatters some more than others.

Every request carries its endpoint id into the result record, so per-endpoint distributions come straight out of the blend. The pattern across 40 endpoints is also what attributes a regression: a uniform absolute shift everywhere points at shared-path cost, a shift confined to the endpoints that read a body points at the parser.

Two rules that keep the blend honest

The weight vector is pinned and versioned as blend-v1. Rotating weights between runs does not survive contact with the arithmetic: per-endpoint latency is not independent of the mix, because changing the mix changes the JIT state that produced it. Reweighting after the fact does not recover comparability. Changing the blend bumps the epoch and re-baselines everything, exactly like changing a barometer.

No endpoint falls below 10 000 requests per target. The ladder delivers 1.38 M requests over the five rungs, so a 0.75% floor on any single endpoint's weight clears 10 350. Anything below that floor gets a median and no percentiles, because 3 000 samples is fine for a median, shaky for p99, and useless for p99.9.

Breadth is also the anti-gaming defence, and a better one than rotation. The weights are public the moment the repo is. With 40 endpoints, anyone who tunes all of them to win has made their framework faster across the board, which is the outcome you were hoping for.

§7

Suite B — capability deltas

Eight suites, 30 s of load and 5 s of settle each, all against one long-lived process.

These are not rankings and they are not absolute throughput. Each suite runs two or more arms against the same process minutes apart, and the published number is the delta between arms. Numerator and denominator therefore come from the same process, the same JIT state and the same minute, which makes capability results the most portable numbers in the benchmark. They survive a host change in a way the blend ratios do not.

Each arm runs at a fixed 3 000 rps, rung 3 of the ladder, which is high enough to be steady and low enough that nothing saturates on the expensive arms.

No capability score. These do not roll up. A framework that is quick at JSON and slow at templates is not usefully described by an average of the two, and any single number here would just re-encode whichever weights you picked.

§8

Suite C — streaming and long-lived connections

Two suites, 120 s each, measuring connections rather than requests.

SSE and WebSockets are not request/response, so the rate ladder and every metric derived from it are meaningless here. What matters instead is how many connections a process can hold, how much memory each one costs, how evenly messages are delivered across all of them, and what a single slow reader does to everyone else.

9 · Server-sent events

Shape. Open 10 000 subscribers, broadcast 10 events/sec for 120 s.

Metrics. Time to first event, delivery latency p50 and p99 measured across subscribers rather than across events, RSS per connection, and whether broadcast latency drifts upward over the window.

The interesting arm. 1% of subscribers read at a tenth of the broadcast rate. A framework that isolates them keeps p99 flat; one that does not stalls the broadcast for everybody, which is the failure people actually hit.

10 · WebSockets

Shape. A 30 s handshake burst to 10 000 connections, then 90 s of echo at 5 msg/sec per connection.

Metrics. Handshakes per second, echo round-trip p50 and p99 at 64-byte and 8 KB frames, RSS per connection, fan-out time to deliver one broadcast to all 10 000, and whether close frames are handled cleanly under load.

Watch for. Frameworks that allocate a full HTTP request context per frame, and thread-per-connection models that fall over well before 10 000.

What is not in caps-v1 yet

In the order I would add them: content negotiation across JSON, XML and MessagePack; CORS preflight, where the OPTIONS path is pure framework overhead and frequently unoptimized; signed cookie and session round-trip; client-disconnect cancellation, which is whether the framework notices a hung-up client and stops doing work; HTTP/2 against HTTP/1.1 on the same blend; keep-alive versus connection churn; and graceful shutdown time under load.

Each one costs 35 seconds per target per capability night, so the budget stretches to roughly fifteen suites before a capability night crosses two hours and needs its own split.

What triggers a re-run

Cache the builds aggressively. Invalidate measurement by blast radius.

Capability suites are versioned independently of the blend, which is the one place the design buys itself some slack. Adding suite 11 does not invalidate suites 1 through 10, because each one is a self-contained delta between arms measured in the same process. Changing the order does invalidate all of them, because order determines the JIT state each suite inherits.

Regression alerting runs against a target's own history within an epoch, not against other frameworks, and never fires on a single night. Require the shift to hold across three consecutive runs of that shard, which is three weeks for the blend and six for capabilities. If six weeks is too slow to be useful for capabilities, promote the one or two suites you care most about into the throughput night rather than shortening the cycle.
