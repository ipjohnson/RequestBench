§1 · What the charts do not say

Every number is attributable and none of them is about testing

For most people choosing a framework, testing is a larger part of the week than a tail latency is.

Every target is wired and measured, and harness/snippets.py points a reader at the lines that produced any published number. Nothing pointed at what it costs to hold those lines to the contract they declare. No target had a test.

The kind was already there and had nothing to mark. spec/marks.json declared rb:test, harness/bundle.py gave /client-exception/ the role test, and EndpointPane.astro rendered it. The only role-test files in the tree were the thirty-three client-exception packages: TypeScript, read by the conformance client, and about one thing, which is the error envelope a framework declares.

§2 · The ordering

A suite that passes while make test fails is the suite that is wrong

Written down before the first suite existed, because thirty-three suites is the problem 5c3e00f deleted, multiplied.

spec/expected.json stays the only authority on what a correct answer is, and the conformance client stays the only thing that judges a target against it. A suite is a second, weaker question: what this framework’s own recommended test facility can say about the target. It never overrides the first.

5c3e00f deleted tests/ for exactly this. It did not know client-exception packages existed, so the moment a framework validated natively the suite would have failed it however correct its own contract said it was.

It follows that a suite is not generated from spec/expected.json. A generated test shows how the generator writes tests, which is the one thing nobody wants to read. The arrange and the act are authored per framework; the floor assertion is a lookup, and it is a port of difference() in client/src/expectation.ts in its order and with its rules, because a suite that is stricter than the client fails a target the client passes and one that is looser passes a target make test rejects.

No code is shared between two frameworks’ suites

The first version put the lookup, the floor and the request builder in one library every .NET suite referenced. That hid the thing being measured. A test for json.small read as three lines on every target, and the four hundred lines it could not run without lived somewhere no page showed, which is the claim that testing is cheap made by leaving the cost out.

It also rested on something no real project has. Five frameworks answering the same payloads at the same paths from one committed file is an oddity of this repository, and a helper built around it measures the oddity. So each suite carries its own copy of what it needs, in its own namespace, and holds only what that target uses: the three WebApplicationFactory suites have no transport-free overloads, and Alba’s has no HttpResponseMessage ones. Sharing inside one framework’s suite is ordinary and stays. Sharing across frameworks does not.

Every helper is marked rb:test for what it serves, so the page shows it beside the test that needed it: * for the lookup, the request builder and the fixture, and authorized.*,body.*,errors.* for the envelope floor, which only the six error endpoints reach. json.small’s page on minimal-apis carries its nine-line test and 442 lines of helpers; errors.unmatched’s carries 558. The classes are longer than the eighty lines block_end scans before giving up, so each one closes with rb:end, which is the documented escape for a block the rule would stop short of.

A helper is shown and not counted. harness/snippets.py records on each part whether its mark named an endpoint or a family or the target, and only the first kind is that endpoint’s test: without that, one mark on a fixture would cover forty-eight endpoints that have no test of their own, and reads_expectation would fail every one of them, because a helper cannot name every endpoint it serves. A mark naming several endpoints by name is still a test of each; the client-exception packages have fourteen of those and they check each endpoint they name.

The floor, in the client’s order

Status, then the kind of body, then the content encoding, then the body. A target answering the right values as text/plain is not answering correctly, so the kind of body is checked before the body. A null in the expectation is a field it deliberately does not pin and is not checked; compressed.gzip_small is the one this family meets.

§3 · The instruction

Generate it the way the framework says to, and do not improve on it

Where the recommended path gives a running test in one command, that is the result. Where it gives nothing, that is also the result, and it is the more interesting one.

The versions are not chosen here. dotnet new xunit on the pinned SDK writes xunit 2.9.3, Microsoft.NET.Test.Sdk 17.14.1 and xunit.runner.visualstudio 3.1.4, and those are what Directory.Packages.props pins. A nicer assertion library would measure the library.

A suite lives in suite/ inside the target it tests, so the test for an endpoint renders beside the handler for it. harness/bundle.py gives that directory role test, which puts it in the bundle and out of code_hash, exactly as prose already is: a sharpened test produces a new page and does not read as a target that changed. The .dockerignore excludes it for the same reason it excludes client-exception/, and Directory.Build.props excludes it from the target’s own compile, which would otherwise put xunit in the measured binary.

§4 · Five targets, four test hosts

What the first language found

Forty-eight endpoints each, which is every endpoint the corpus has. compressed and middleware were written first, because they are the two families where a test can pass and prove nothing.

What compressed was supposed to catch, and did not

Compression is sometimes a framework middleware and sometimes a server setting, and an in-memory test sees only the first kind. All five .NET targets are the first kind: each compresses inside the request pipeline, on these three routes alone, so that the other forty-two do not pay a did the client ask? check. An in-memory transport reaches the codec on all five, and the transport field in spec/matrix.json says testserver five times. The field earns its keep in the language where that stops being true, which is not this one.

None of this starts a process or binds a port. All five suites resolve IServer to Microsoft.AspNetCore.TestHost.TestServer, including the two that do not use WebApplicationFactory directly: FastEndpoints’ AppFixture wraps it, and Alba hands back a TestHost.ResponseBodyReaderStream. The listening on 8080 line each target prints is its own Console.Error statement, which runs whether or not anything is listening. UseUrls is ignored.

The socket case is also one process. WebApplicationFactory.UseKestrel(0) followed by StartServer() replaces the in-memory transport with a real KestrelServerImpl on a loopback port, in the test’s own process, and CreateClient() then talks HTTP to it. Measured on minimal-apis: server=KestrelServerImpl base=http://127.0.0.1:58707/, same pid, same gzipped 19,141 bytes as the in-memory run. So transport has three values and not two, and the family that needs a real port in .NET costs a line rather than a second process. The suites stay on testserver because that is what the documentation leads with and because the negative test above proves it reaches the codec.

The trap that did fire is the client, not the host. Most test clients decode transparently, and one that did would make every gzip assertion pass against an identity response. Four of the five suites use the plain client for that reason, and the gzip is undone by the floor assertion where the comparison needs it rather than by the transport. Alba does not have the problem at all, because it hands back the response the endpoint wrote.

compressed.gzip_small is the endpoint the expectation does not pin. The payload sits under the shared 1,024-byte floor, the contributing frameworks disagree, and unpinned records the disagreement rather than choosing a winner. The floor assertion skips the field and each suite asserts what its own target does, which for all five .NET targets is identity.

Where the request comes from

A suite writes its own arrange and its own act, because the difference between two frameworks there is the thing being captured. The values in the request are not the suite’s to choose. spec/plan.json is where an order id, a query string and a request body come from, and a test that typed one out would be asserting against a request the measurement never sends. Instance zero always, because an endpoint sends up to 512 of them and a failure that picked a different one each run would not reproduce.

One endpoint cannot be sent at all until the target has answered a different one. etag.match_large carries an if-none-match the target itself has to issue, so its test asks for /etag/large, takes the validator off the response and sends the conditional request with it. That is the endpoint’s own shape rather than something the suite decided to do, and spec/plan.json says so in its captures block.

What an error endpoint is judged against

Not spec/expected.json’s errors block, which is what caught this on the first full run. That block says what the plan intends, and a framework is allowed to declare otherwise: the client-exception package beside each target is where it does, and minimal-apis uses it to say that a body AddValidation could not read is a bare 400 and not the 422 the plan asks for. Those packages are TypeScript read by the conformance client, so reconciling the two is the client’s job and not a suite’s.

A suite reads the envelope this target recorded instead: the status, the kind of body, and the shape, which is the envelope with the values taken out. The shape rather than the body, because ASP.NET’s ProblemDetails carries a traceId that changes per connection and an exact body could never match twice. Shape.Of is a port of shape_of() in harness/expected.py, which is what wrote those shapes.

What middleware can hold

The layers are no-ops, so nothing they do is visible in a response and no assertion over one can tell four apart from sixteen. What a test can hold is the thing that goes wrong in practice: a test that calls the handler rather than the app passes while the layers never ran. FastEndpoints and Wolverine make that unusually easy, because an endpoint is a class anyone can new up and an endpoint method is a static function. Going through the test host is what puts the layers back in the path, and that is the whole of what these three tests assert.

Proven to bite, not just to pass

A suite that passes says nothing until something has been broken under it. Four breakages, each reverted:

BrokenCaught by

§5 · The marks change

A required kind that cannot use required: "every"

Two of the three planned assertions did not survive contact with the corpus. What replaced them is below.

harness/snippets.py drops every record that lacks a kind marked every, so setting it on test would empty the snippet map for all forty-eight endpoints on all thirty-three targets and the site would render nothing at all. required: "ratchet" is the third value: absence is counted against the committed allowance, which only ever goes down, and the filter stays keyed to handler alone. The allowance today is 1,247 endpoints with no test out of 1,584, and 337 held by one. The five .NET targets are off it entirely; twenty-eight remain.

reads_expectation

A test snippet has to name the endpoint it is marked for, which is the key spec/expected.json is read by. This is what stops 1,584 hand-written assertions drifting away from the file that decides what a correct answer is, and it catches the second thing mentions_dep catches: a mark that drifted onto neighbouring lines stops naming its endpoint, and a drifted mark is otherwise indistinguishable from a correct one.

asserts_status, which is not here

It contradicts reads_expectation. The status lives in spec/expected.json; a test that writes it out as a literal is the drift the other assertion exists to stop. Reaching the expectation is asserting the status, and a second check that demanded the literal would fail every correct test.

The facility declaration, which is a requirement rather than an assertion

The plan was a names_facility assertion over the snippet, on the reasoning that produced mentions_dep. It cannot work: the facility is named in the fixture class, not in the test method, so a per-snippet check fails every correct test in the corpus. The check is a requirement instead, mirroring the declared rule for wiring. A family with a marked test has to declare a facility and a transport in spec/matrix.json under suites, and the dependency it names has to be in that target’s own suite project rather than in the target’s manifest, because a test host in a target’s manifest would be a test host in the measured binary.

It is declared per family and not per target, because whether a test runs in the process or over a socket is not a fact about a framework: MockMvc and @SpringBootTest(webEnvironment = RANDOM_PORT) are both Spring, and a target that reaches for a socket on compressed and nothing else is the case a per-target flag would hide.

The client-exception packages owe nothing here. They describe the envelope a framework declares and run against no booted target, so there is no facility and no transport to name. They still count for coverage, because holding a target to the contract it declares is what the kind is for.

Two sections on the page

EndpointPane.astro said Contract test, which was right for the client-exception packages and wrong once the same section also carried the endpoint’s own test. They are not the same claim, so they are not one heading: a suite boots the target and holds it to spec/expected.json, and an envelope package describes what the framework declares and boots nothing.

§6 · What is not here

The order the rest goes in

  1. The other five languages

    Java next, because its test facilities are the most opinionated and least alike, and because compressed there is where the per-family transport field stops saying testserver five times.

  2. The client projects

    Not started. The framework-shaped question is whether a framework describes its own routes well enough that a client can be generated from the description rather than written, and it needs the OpenAPI question settled per target first.

    One thing is already known and is why SUITE in harness/bundle.py catches /client/ before the name rules. A file called openapi.json is role contract, which handler reads and which is cardinality: one. A document written out of a target’s routes therefore registers every one of them a second time, and dropping one into a target that also routes in code turns all forty-eight of its endpoints into the §7 ambiguity error. openapi.yaml does not trip it only because route_regex wants a quote on both sides of the path and a YAML key has none, which is luck and not a design.
