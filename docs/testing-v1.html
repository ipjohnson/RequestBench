Target Suites

§1 · What the charts do not say

Every number is attributable and none of them is about testing

For most people choosing a framework, testing is a larger part of the week than a tail latency is.

Every target is wired and measured, and harness/snippets.py points a reader at the lines that produced any published number. Nothing pointed at what it costs to hold those lines to the contract they declare. No target had a test.

The kind was already there and had nothing to mark. spec/marks.json declared rb:test, harness/bundle.py gave /client-exception/ the role test, and EndpointPane.astro rendered it. The only role-test files in the tree were the thirty-three client-exception packages: TypeScript, read by the conformance client, and about one thing, which is the error envelope a framework declares.

§2 · The ordering

A suite that passes while make test fails is the suite that is wrong

Written down before the first suite existed, because thirty-three suites is the problem 5c3e00f deleted, multiplied.

spec/expected.json stays the only authority on what a correct answer is, and the conformance client stays the only thing that judges a target against it. A suite is a second, weaker question: what this framework’s own recommended test facility can say about the target. It never overrides the first.

5c3e00f deleted tests/ for exactly this. It did not know client-exception packages existed, so the moment a framework validated natively the suite would have failed it however correct its own contract said it was.

It follows that a suite is not generated from spec/expected.json. A generated test shows how the generator writes tests, which is the one thing nobody wants to read. The arrange and the act are authored per framework; the floor assertion is a lookup, and it is a port of difference() in client/src/expectation.ts in its order and with its rules, because a suite that is stricter than the client fails a target the client passes and one that is looser passes a target make test rejects.

No code is shared between two frameworks’ suites

The first version put the lookup, the floor and the request builder in one library every .NET suite referenced. That hid the thing being measured. A test for json.small read as three lines on every target, and the four hundred lines it could not run without lived somewhere no page showed, which is the claim that testing is cheap made by leaving the cost out.

It also rested on something no real project has. Five frameworks answering the same payloads at the same paths from one committed file is an oddity of this repository, and a helper built around it measures the oddity. So each suite carries its own copy of what it needs, in its own namespace, and holds only what that target uses: the three WebApplicationFactory suites have no transport-free overloads, and Alba’s has no HttpResponseMessage ones. Sharing inside one framework’s suite is ordinary and stays. Sharing across frameworks does not.

Every helper is marked rb:test for what it serves, so the page shows it beside the test that needed it: * for the lookup, the request builder and the fixture, and authorized.*,body.*,errors.* for the envelope floor, which only the six error endpoints reach. json.small’s page on minimal-apis carries its nine-line test and 442 lines of helpers; errors.unmatched’s carries 558. The classes are longer than the eighty lines block_end scans before giving up, so each one closes with rb:end, which is the documented escape for a block the rule would stop short of.

A helper is shown and not counted. harness/snippets.py records on each part whether its mark named an endpoint or a family or the target, and only the first kind is that endpoint’s test: without that, one mark on a fixture would cover fifty endpoints that have no test of their own, and reads_expectation would fail every one of them, because a helper cannot name every endpoint it serves. A mark naming several endpoints by name is still a test of each; the client-exception packages have fourteen of those and they check each endpoint they name.

The floor, in the client’s order

Status, then the kind of body, then the content encoding, then the body. A target answering the right values as text/plain is not answering correctly, so the kind of body is checked before the body. A null in the expectation is a field it deliberately does not pin and is not checked; compressed.gzip_small is the one this family meets.

§3 · The instruction

Generate it the way the framework says to, and do not improve on it

Where the recommended path gives a running test in one command, that is the result. Where it gives nothing, that is also the result, and it is the more interesting one.

The versions are not chosen here. dotnet new xunit on the pinned SDK writes xunit 2.9.3, Microsoft.NET.Test.Sdk 17.14.1 and xunit.runner.visualstudio 3.1.4, and those are what Directory.Packages.props pins. A nicer assertion library would measure the library.

A suite lives in suite/ inside the target it tests, so the test for an endpoint renders beside the handler for it. harness/bundle.py gives that directory role test, which puts it in the bundle and out of code_hash, exactly as prose already is: a sharpened test produces a new page and does not read as a target that changed. The .dockerignore excludes it for the same reason it excludes client-exception/, and Directory.Build.props excludes it from the target’s own compile, which would otherwise put xunit in the measured binary.

§4 · Five targets, four test hosts

What the first language found

Forty-eight endpoints each, which is every endpoint the corpus has. compressed and middleware were written first, because they are the two families where a test can pass and prove nothing.

TargetFacilityWhat it cost
minimal-apisWebApplicationFactoryOne line in Program.cs: top-level statements compile to an internal Program the factory cannot name.
aspnet-mvcWebApplicationFactoryThe same host, for a framework that shares nothing else with minimal APIs. Its documented alternative, calling the action directly, would never run the filter compressed is wired with.
carterWebApplicationFactoryNo first-party test package. Not a gap: Carter routes onto minimal APIs, so the cost of testing it is the cost of testing the thing underneath it.
fastendpointsFastEndpoints.TestingThe only framework here shipping its own. It is built on xunit.v3, a Microsoft Testing Platform runner, so this target runs a different xunit major than the four beside it, is an executable rather than something VSTest hosts, and is refused outright by dotnet test on the .NET 10 SDK when it shares a solution with them. It runs on its own under dotnet run.
wolverine-httpAlbaNamed by Wolverine’s own documentation. It runs a scenario against the application’s HttpContext rather than handing back an HttpResponseMessage, and TestServer’s response body is forward-only, so it is read once and never rewound.

What compressed was supposed to catch, and did not

Compression is sometimes a framework middleware and sometimes a server setting, and an in-memory test sees only the first kind. All five .NET targets are the first kind: ASP.NET Core’s response compression middleware runs inside the request pipeline, on the whole application, so every endpoint pays a did the client ask? check. An in-memory transport reaches the codec on all five, and the transport field in spec/matrix.json says in-memory five times. The field earns its keep in the language where that stops being true, which turned out to be the next one: see Sanic below.

None of this starts a process or binds a port. All five suites resolve IServer to Microsoft.AspNetCore.TestHost.TestServer, including the two that do not use WebApplicationFactory directly: FastEndpoints’ AppFixture wraps it, and Alba hands back a TestHost.ResponseBodyReaderStream. The listening on 8080 line each target prints is its own Console.Error statement, which runs whether or not anything is listening. UseUrls is ignored.

The socket case is also one process. WebApplicationFactory.UseKestrel(0) followed by StartServer() replaces the in-memory transport with a real KestrelServerImpl on a loopback port, in the test’s own process, and CreateClient() then talks HTTP to it. Measured on minimal-apis: server=KestrelServerImpl base=http://127.0.0.1:58707/, same pid, same gzipped 19,141 bytes as the in-memory run. So transport has three values and not two: in-memory for a client that calls the application with no socket at all, loopback for a real server on a loopback port in the test’s own process, and process for a target booted the way harness/run.py boots one. The family that needs a real port in .NET costs a line rather than a second process. The suites stay in-memory because that is what the documentation leads with and because the negative test above proves it reaches the codec. The first version of this field named the values testserver and kestrel, which are ASP.NET’s words for them; the second language made that wrong.

The trap that did fire is the client, not the host. Most test clients decode transparently, and one that did would make every gzip assertion pass against an identity response. Four of the five suites use the plain client for that reason, and the gzip is undone by the floor assertion where the comparison needs it rather than by the transport. Alba does not have the problem at all, because it hands back the response the endpoint wrote.

compressed.gzip_small is the endpoint the expectation does not pin. The payload is 125 bytes, the contributing frameworks disagree about compressing it, and unpinned records the disagreement rather than choosing a winner. The floor assertion skips the field and each suite asserts what its own target does. For all five .NET targets that is gzip, because ASP.NET Core’s response compression has no minimum size.

Where the request comes from

A suite writes its own arrange and its own act, because the difference between two frameworks there is the thing being captured. The values in the request are not the suite’s to choose. spec/plan.json is where an order id, a query string and a request body come from, and a test that typed one out would be asserting against a request the measurement never sends. Instance zero always, because an endpoint sends up to 512 of them and a failure that picked a different one each run would not reproduce.

One endpoint cannot be sent at all until the target has answered a different one. etag.match_large carries an if-none-match the target itself has to issue, so its test asks for /etag/large, takes the validator off the response and sends the conditional request with it. That is the endpoint’s own shape rather than something the suite decided to do, and spec/plan.json says so in its captures block.

What an error endpoint is judged against

Not spec/expected.json’s errors block, which is what caught this on the first full run. That block says what the plan intends, and a framework is allowed to declare otherwise: the client-exception package beside each target is where it does, and minimal-apis uses it to say that a body AddValidation could not read is a bare 400 and not the 422 the plan asks for. Those packages are TypeScript read by the conformance client, so reconciling the two is the client’s job and not a suite’s.

A suite reads the envelope this target recorded instead: the status, the kind of body, and the shape, which is the envelope with the values taken out. The shape rather than the body, because ASP.NET’s ProblemDetails carries a traceId that changes per connection and an exact body could never match twice. Shape.Of is a port of shape_of() in harness/expected.py, which is what wrote those shapes.

What middleware can hold

The layers are no-ops, so nothing they do is visible in a response and no assertion over one can tell four apart from sixteen. What a test can hold is the thing that goes wrong in practice: a test that calls the handler rather than the app passes while the layers never ran. FastEndpoints and Wolverine make that unusually easy, because an endpoint is a class anyone can new up and an endpoint method is a static function. Going through the test host is what puts the layers back in the path, and that is the whole of what these three tests assert.

Proven to bite, not just to pass

A suite that passes says nothing until something has been broken under it. Four breakages, each reverted:

BrokenCaught by
the shared payload, small answering medium17 tests across 9 families, on all five targets
the JSON naming policy, snake_case to camelCase35 tests across 12 families

the plaintext literal, one changed letterbaseline.plaintext: 'Hello, world!' vs 'Hello, World!'

Every family is covered by at least one of the four.

§4a · Six Python targets, six facilities

What the second language found

Every Python framework here brings its own test client, and no two of them are the same thing.

TargetFacilityWhat it cost
fastapiTestClient, pytestFastAPI’s TestClient is Starlette’s, and at the pinned Starlette it wants httpx2: it imports that first, falls back to httpx with a deprecation warning, and its own error says pip install httpx2. FastAPI’s testing documentation still says to install httpx. The suite installs what the client it runs asks for.
starletteTestClient, pytestThe same client and the same httpx2. Its compression is GZipMiddleware attached per route, which is ASGI middleware and reached in memory.
litestarlitestar.testing, pytestShips with the framework and is built on httpx, not the httpx2 Starlette moved to, so the two ASGI frameworks here that ship a client ask for different transports. The 23 warnings a run prints are the target’s own route declarations using a deprecated query-parameter style, which is target code and not the suite’s.
flaskapp.test_client(), pytestNothing to install beyond pytest. The fixtures are the ones Flask’s documentation writes, TESTING included, and TESTING is not inert: it propagates an unhandled exception into the test rather than answering 500 with it. Werkzeug’s client does not decode gzip, so the bytes as sent come for free.
sanicsanic-testing, pytestThe one that crosses a socket. app.test_client starts the application on a random loopback port with app.run() for every request, sends one request over httpx and stops it again: the suite takes 1.6 seconds where the in-memory five take 0.1 to 0.2, and the 199 warnings it prints are Sanic’s server startup calling asyncio APIs Python 3.14 has deprecated, once per boot. Its newest release is 24.6.0 against a pinned Sanic of 25.12.1; it declares no bound and it works, which a suite has to find out rather than read. It also reads every response in full, so the body arrives already decoded and there is no raw stream to reach.
django-asgiAsyncClient, DiscoverRunnerNot pytest. Django’s tests are unittest classes run by its own DiscoverRunner, and for code that is not a project with a manage.py its documentation’s answer is a runtests.py calling get_runner(settings). The runner switches the test environment on and runs Django’s system checks before any test, neither of which a pytest suite would show. self.async_client never serializes a request, so response.content is the bytes the view wrote, gzip_page’s included.

transport stops saying one thing. Five targets are in-memory and Sanic is loopback, and that is a fact about the helper its documentation reaches for rather than about the framework: app.asgi_client from the same package would have been in memory.

The client trap is sharper here than in .NET. Every httpx-based client decodes gzip before .content sees it, so the three suites built on one read the body through iter_raw(). Sanic’s cannot: sanic-testing hands back no stream. Its suite’s floor.py is the only one with no decode step, and says why. The encoding check there rests on the content-encoding header, which is still a real check, because httpx raises on a body the header describes wrongly.

The same helpers are shorter in Python. A FastAPI endpoint’s page carries its six-line test and 257 lines of helpers; minimal-apis carries nine and 442 for the same lookup, floor and request builder. Breaking the shared payload fails 17 tests in every one of the six suites, which is the count the .NET suites gave for the same break.

Each suite has its own requirements.in, compiled with a -c ../../requirements.txt line, which is pip-tools’ layered-requirements pattern: a test dependency may not resolve a different version of anything a target already runs. Django’s suite installs nothing and has no file.

§4b · Five Node targets, four runners

What the third language found

Each suite runs under the runner its framework’s documentation uses, or that the tool it reaches for does, and that is four different runners for five targets.

TargetFacilityWhat it cost
fastifyinject(), node:testNothing to install. Fastify’s testing guide ships inside the package and runs inject(), which is light-my-request, under node:test. rawPayload is the bytes as the reply wrote them. It answers its 304 with content-type: application/json, which RFC 9110 §15.4.5 says a server SHOULD NOT send; the spec leaves that unpinned and so does the suite.
honoapp.request(), VitestHono’s guide says Vitest and app.request(), which hands a Request to the application’s own fetch handler and returns the Response it made, with nothing between to decode it. Its compress middleware gzips compressed.gzip_small’s 125 bytes into 123, which is the one thing that endpoint exists to ask, and the suite pins it.
h3app.request(), node:testh3’s guide gives app.request() as testing without listening and names no runner, so the suite uses the one built into Node and installs nothing.
expresssupertest, MochaNo testing guide; supertest is what the ecosystem reaches for, and its README writes its examples for Mocha. It binds the application to an ephemeral loopback port. Its superagent unzips gzip before anything can read it, and sets Accept-Encoding: gzip, deflate on every request with no way to leave it off, so the suite sends identity wherever the plan names no encoding.
koasupertest, MochaThe same, handed app.callback(). koa-compress is mounted on the three compressed routes alone and nothing else answered gzip when asked.

What the Express suite found in the Express target

With superagent’s default header on, eight Express endpoints outside the compressed family answered gzip: every one over the 1,024-byte floor in the etag, cache, body, domain and template families. The target’s own comment says its compression middleware sits on a router carrying only the three compressed routes, so that the other endpoints do not pay a did the client ask? check. The router does carry only those routes, but routes.use(gzip) is router-level middleware and app.use(routes) mounts that router at the root, so the check runs on every request that passes through it, which is every family registered after compressed.

make test cannot see this, because the conformance client never asks for gzip on those endpoints and so never gets it. The bodies it measures are right. What is wrong is that roughly twenty endpoints carry a middleware their rows were meant to be measured without, which is the contamination the compressed family was given its own paths to avoid. It is target code, and it is not fixed here: app.use("/compressed", routes), or the middleware on each route, would scope it.

transport splits three and two: fastify, hono and h3 are in-memory, express and koa are loopback. The Node domain resolves the fixture relative to its own file, so unlike the .NET and Python suites these set no RB_FIXTURE. The helpers are the shortest of the three languages: an error endpoint’s page carries 230 lines of them on Fastify, against 311 on FastAPI and 558 on minimal-apis. Breaking the shared payload fails 17 tests in each of the five suites, the count every .NET and Python suite gave.

§4c · Six Java targets, and what their test modes change

What the fourth language found

Each suite starts from what that framework’s own project generator writes: Spring Initializr, code.quarkus.io, Micronaut Launch, start.vertx.io, and the documentation where there is no generator.

TargetFacilityWhat it cost
spring-boot@SpringBootTest, MockMvcThe one Java suite that runs in memory. Boot’s reference says so: “By default, @SpringBootTest does not start the server but instead sets up a mock environment”. The compressed tests are the exception: Tomcat’s connector does the compressing and MockMvc never reaches it, so they start the server on a random port. Boot 4 split spring-boot-starter-test into a test starter per technology, and Initializr writes three for this target’s three starters. @SpringBootTest never calls main(), which is where the fixture is loaded, so the suite loads it. It answers its 304 with content-type: application/json.
quarkus@QuarkusTest, REST AssuredStarts the application’s HTTP server in the test JVM. The generator now writes quarkus-junit, no longer quarkus-junit5. The one target whose startup work its test host does, because it loads the fixture on the StartupEvent. REST Assured sends Accept-Encoding: gzip,deflate and decodes; noContentDecoders() turns both off. And @QuarkusTest cannot see the envelope this target sends in production for a body it could not bind: see below.
micronaut@MicronautTest, @ClientStarts the embedded server on a random port. The declarative client decodes gzip and then removes Content-Encoding, so a compressed answer and an identity one are indistinguishable until micronaut.http.client.decompression-enabled is turned off in application-test.properties. The blocking client throws on anything of 400 or above, so every error endpoint’s answer is recovered out of an exception.
helidon-se@ServerTest, Http1ClientThe example Helidon’s documentation leads with, which it says “starts the server (opens ports)”; @RoutingTest is the one it calls the unit test. The server is started, and the routes built, before any @BeforeAll, so the fixture is loaded in @SetUpRoute. @SetUpServer turns on the gzip content encoding through the same Main.server the target calls, and the suite turns the injected client’s content encoding discovery off, because with the gzip module present it decodes gzip and keeps Content-Encoding. uri() takes no query string and entity() throws on a 204 or a 304. The BOM the target imports manages the testing module and not JUnit, so JUnit is the 5.12.2 Helidon tests itself with.
vertxVertxExtension, WebClientThe one target whose code had to change: its router was built inline in main(), so nothing could reach it without starting the target on its container port. Main.router(vertx) now builds it and main() calls the same method; conformance is 48/48 from the image before and after. The suite’s server is built with Main.options() too, which is where compression is turned on. The suite first drove it with the core HttpClient, which hands a response’s body to whatever is listening when it arrives, and lost one now and then: middleware.sixteen once read a 200 with nothing in it, in CI and never locally. WebClient, which vertx-junit5’s documentation uses, reads the whole body before it returns. The starter pins JUnit 5.9.1.
javalinJavalinTest, testtools clientStarts the application on a random port for every test, and a stopped Javalin cannot be restarted, so every test builds its own. The client in Javalin 7’s test tools is built on the JDK’s and reads every body as a String, which makes a gzip body unrecoverable; those requests go to the origin JavalinTest started, by hand, with a byte-array handler. It brings no test runner, and Javalin’s testing tutorial is still written for Javalin 6 with JUnit 4, so there is nothing current to follow.

What @QuarkusTest cannot see

Asked to bind {"customer_id":"not-an-int"}, the Quarkus target answers {"objectName":"Class","attributeName":"customer_id","line":1,"column":16,"value":"not-an-int"} under @QuarkusTest. The packaged jar answers a bare 400 that the target’s BodilessErrors filter turns into the envelope spec/expected.json records. Quarkus’s own BuiltinMismatchedInputExceptionMapper builds its detailed body only when LaunchMode.current().isDevOrTest(), and @QuarkusTest runs in test launch mode whatever profile it is given: running it with the prod profile changes nothing. So the recommended Quarkus test, of the recommended Quarkus application, observes an answer production never sends, and only @QuarkusIntegrationTest against the packaged jar, in a process of its own, could see the real one. The two body.rejected_* tests hold what it can see, the recorded status and a JSON body, and say why.

This is the finding the issue expected from compressed and did not get there: a test mode that does not run the code under test. It arrived through error handling instead.

The rest

transport is in-memory once and loopback five times, and loopback for all six on compressed. Java’s facilities overwhelmingly start a real server, which is the inverse of .NET. All six targets compress with their server’s own compression, which only a running server reaches, so spring-boot’s compressed tests start one.

The JUnit version is not a thing the Java frameworks agree on: 5.9.1 from Vert.x’s starter, 5.12.2 from Helidon’s own build, 6.1 under Spring Boot 4.1, each suite on the one its tooling picked. A suite lives in its module’s src/test, because that is where Maven compiles it and where all three annotation-driven frameworks expect to run, so harness/bundle.py gives /src/test/ the role test and .dockerignore keeps it out of the image. Its dependencies are test-scoped in the module’s own pom, and the facility check accepts a test-scoped declaration there and refuses a compile-scoped one: moving vertx-junit5 to compile scope raises fourteen complaints.

An error endpoint’s page carries 359 lines of helpers on Spring Boot and 390 on Javalin, against 230 on Fastify, 311 on FastAPI and 558 on minimal-apis. Breaking the shared payload fails 17 tests in each of the six suites, as it did in every other language. The Java suites were built and run in the maven:3.9-eclipse-temurin-25 image, which is what make suites falls back to when there is no mvn on the path; all six run in one reactor build in 23 seconds.

§4d · Five Go targets, one package each

What the fifth language found

Go decides where a test goes: a _test.go file in the package it tests. For a package main that is the only way in.

TargetFacilityWhat it cost
ginhttptest, ServeHTTPWhat Gin’s testing documentation does: a request handed to the engine’s ServeHTTP and a ResponseRecorder to catch the answer. It gzips compressed.gzip_small’s 125 bytes into 127.
echohttptest, ServeHTTPNot what Echo’s guide does. The guide calls a handler directly with a context from e.NewContext, and composes middleware by hand. That needs handlers a test can name, and this target registers closures; and it skips every route-scoped middleware, which is what five of the fourteen families are made of, so a test written that way would pass while the layers never ran. The guide asserts with testify, which would be a new requirement in the go.mod all five Go targets share. It gzips the small payload into 132 bytes.
chihttptest, ServeHTTPNo testing guide, and a chi router is an http.Handler, so the standard library’s shape needs nothing else. Small payload: 128 bytes.
gorilla-muxhttptest, ServeHTTPWhat its README tests a route with, and for the README’s reason: going through the router is what makes mux.Vars work. Small payload: 128 bytes.
fiberapp.Test()Fiber is built on fasthttp, which is not an http.Handler, so the approach the other four share cannot reach it at all. app.Test takes a net/http request, runs it over an in-memory connection and hands back a net/http response. It is the one Go target that leaves the small payload alone, and it answers its 304 with content-type: application/json; charset=utf-8.

What Go asked of the targets

All five built their router inline in main(), the way Vert.x did, and httptest needs the router as a value. Each now has a router() that main() serves; the marks moved with the code they label, the snippet counts are identical before and after, and all five answer spec/expected.json 48/48 from their images.

A Go test shares its package with the code it tests, and so its namespace. Echo, chi, gorilla/mux and Fiber each declare a package-level gzip in compressed.go, so the standard library’s compress/gzip has to be imported under another name in their suites, and every helper has a name long enough not to meet the send, fail and ok the targets already have. There is nothing to install: net/http/httptest and testing are the standard library and app.Test ships with Fiber, so go.mod is untouched. There is no assertion library either, so a check above the floor is an if and a t.Fatalf, which is what Go tests look like.

transport is in-memory for all five, like .NET and unlike Java. Four of the five gzip a payload under the shared floor and every one of them makes it bigger, which is the whole of what compressed.gzip_small is there to show. An error endpoint’s page carries 443 lines of helpers on Echo. Breaking the shared payload fails 17 tests in each of the five suites. Five files in these targets were not gofmt-clean before this change and are left as they were; reformatting would move their code_hash for nothing.

§4e · Six Rust targets, one test module each

What the sixth language found

Rust decides where a unit test goes: a #[cfg(test)] module in the crate it tests. An integration test in tests/ can only reach a library’s public API, and every Rust target is a binary with no library, so each suite is a test module of the binary. It lives in src/suite/, which the /suite/ rule in harness/bundle.py already gives the role test.

TargetFacilityWhat it cost
axumtower, oneshotWhat axum’s testing example does. The Router is a tower Service, and ServiceExt::oneshot hands it one request. axum is built on tower, so nothing new is declared for it. It gzips compressed.gzip_small’s 125 bytes into 125, which the unpinned block in spec/expected.json already recorded.
actix-webtest::init_serviceWhat actix-web’s testing documentation does. init_service builds the App in the process and call_service hands it a request, under actix’s own #[actix_web::test]. The routes moved into a config() that both the server’s App and the test’s are built with, through App::configure. It answers its 304 with content-type: application/json.
rocketlocal::blocking::ClientThe client Rocket’s testing guide uses in its examples. It dispatches to the application with no socket, and it is synchronous, so these are the only Rust tests that are plain #[test]s. Rocket has no compression of its own. The target gzips anything over 32 bytes by hand, so the small payload is gzipped too.
poempoem::test::TestClientBehind poem’s test feature, so the target declares poem a second time under [dev-dependencies] with the feature on. Its Compression middleware sends no Vary with a gzip body.
salvosalvo::test::TestClientBehind salvo’s test feature, declared the way poem’s is. Salvo’s testing documentation reads a response with take_string, which decodes gzip, so the floor would be handed a body the target never sent. The suite reads it with take_bytes. Its Compression handler sends Vary: accept-encoding with a gzip body, and it leaves a body under its 1024-byte min_length uncompressed, so the small payload goes out as it is. It answers its 304 with content-type: application/json; charset=utf-8.
warpwarp::test::request()What warp’s documentation tests a filter with: a request run through the filter in the process, and the http::Response it produced. Since warp 0.4 it is behind warp’s test feature, declared the way poem’s is. warp::compression::gzip() sends no Vary either.

What Rust asked of the targets

All six built their application inline in main(), the way the Go targets and Vert.x did. Each now has a function that builds it and that main() serves: app() on axum and poem, config() on actix-web, rocket() on Rocket, service() on salvo and routes() on warp. The marks moved with the code they label, the snippet counts are identical before and after, and all six answer spec/expected.json 48/48 from their images.

The standard library has no gzip decoder, so every suite declares flate2 under [dev-dependencies], which is Cargo’s test scope. The workspace already pinned it, because rocket gzips with it. The workspace resolver is "3", which keeps a dev-dependency’s features out of the release build, so the test features of poem, salvo and warp never reach the measured binary. test_dependency() now reads [dev-dependencies], and a facility declaration names a feature as poem/test. A release build never looks for a module behind #[cfg(test)], so .dockerignore keeps src/suite/ out of the image the way it keeps Java’s src/test/ out.

transport is in-memory for all six, like .NET and Go. Five of the six Rust targets gzip a payload under the shared floor, and all five end at 125 bytes, no smaller than they started. salvo sends it uncompressed. poem and warp send a gzip body with no Vary: Accept-Encoding, because neither compressor sets it. Five of the six Java servers do the same, and only Tomcat sets it. Their compressed.gzip_large tests say so and do not hold them to it, because spec/expected.json does not pin Vary. An error endpoint’s page carries 344 lines of helpers on warp and 361 on salvo. Breaking the shared payload fails 17 tests in each of the six suites. The Rust suites were built and run in the rust:1.98-slim image, which is what make suites falls back to when there is no cargo on the path. All six run in one cargo test in 5 seconds once the build is cached.

§5 · The marks change

A required kind that cannot use required: "every"

Two of the three planned assertions did not survive contact with the corpus. What replaced them is below.

harness/snippets.py drops every record that lacks a kind marked every, so setting it on test would empty the snippet map for all fifty endpoints on all thirty-three targets and the site would render nothing at all. required: "ratchet" is the third value: absence is counted against the committed allowance, which only ever goes down, and the filter stays keyed to handler alone. The allowance is empty now. All 1,650 are held by a test, and a target that drops one fails the check.

reads_expectation

A test snippet has to name the endpoint it is marked for, which is the key spec/expected.json is read by. This is what stops 1,650 hand-written assertions drifting away from the file that decides what a correct answer is, and it catches the second thing mentions_dep catches: a mark that drifted onto neighbouring lines stops naming its endpoint, and a drifted mark is otherwise indistinguishable from a correct one.

asserts_status, which is not here

It contradicts reads_expectation. The status lives in spec/expected.json; a test that writes it out as a literal is the drift the other assertion exists to stop. Reaching the expectation is asserting the status, and a second check that demanded the literal would fail every correct test.

The facility declaration, which is a requirement rather than an assertion

The plan was a names_facility assertion over the snippet, on the reasoning that produced mentions_dep. It cannot work: the facility is named in the fixture class, not in the test method, so a per-snippet check fails every correct test in the corpus. The check is a requirement instead, mirroring the declared rule for wiring. A family with a marked test has to declare a facility and a transport in spec/matrix.json under suites, and the dependency it names has to be in that target’s own suite project rather than in the target’s manifest, because a test host in a target’s manifest would be a test host in the measured binary.

It is declared per family and not per target, because whether a test runs in the process or over a socket is not a fact about a framework: MockMvc and @SpringBootTest(webEnvironment = RANDOM_PORT) are both Spring, and a target that reaches for a socket on compressed and nothing else is the case a per-target flag would hide.

The client-exception packages owe nothing here. They describe the envelope a framework declares and run against no booted target, so there is no facility and no transport to name. They still count for coverage, because holding a target to the contract it declares is what the kind is for.

Two sections on the page

EndpointPane.astro said Contract test, which was right for the client-exception packages and wrong once the same section also carried the endpoint’s own test. They are not the same claim, so they are not one heading: a suite boots the target and holds it to spec/expected.json, and an envelope package describes what the framework declares and boots nothing.

§6 · What is not here

The order the rest goes in

  1. The client projects

    Not started. The framework-shaped question is whether a framework describes its own routes well enough that a client can be generated from the description rather than written, and it needs the OpenAPI question settled per target first.

    One thing is already known and is why SUITE in harness/bundle.py catches /client/ before the name rules. A file called openapi.json is role contract, which handler reads and which is cardinality: one. A document written out of a target’s routes therefore registers every one of them a second time, and dropping one into a target that also routes in code turns all fifty of its endpoints into the §7 ambiguity error. openapi.yaml does not trip it only because route_regex wants a quote on both sides of the path and a YAML key has none, which is luck and not a design.
