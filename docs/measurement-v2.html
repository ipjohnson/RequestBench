Measurement v2

Publish real times instead of ratios. One dedicated machine with a fixed clock makes absolute numbers reproducible, which makes them publishable, which is what a reader needed in the first place: latency in milliseconds at a traffic level they recognise.

§1 · The reversal

Nothing absolute was published because the machine moved

That rule was a mitigation, not a principle. The mitigation goes when its cause does.

Every result used to be a ratio to a bare baseline measured in the same run, because every run landed on a different GitHub-hosted machine and a ratio divides the machine out. The rule worked for what it was for. It also threw away the number a reader came for, and it was never as clean as it looked. The baselines have since been removed outright: hand-rolled segment dispatch is a second implementation to maintain and to answer questions about, and once nothing divides by it there is no job left for it but the response fingerprint, which the language's anchor now holds.

A run on 15 September measured node-http, then fastify, then node-http again: the same image at both ends, ten minutes apart, nothing else on the box.

Fastify's published ratio at rung 1 is 0.67 against the first baseline and 1.04 against the second. The choice of denominator decides whether the site reports Fastify as faster than bare node:http or level with it. At rung 5 the same choice moves it from 0.91 to 0.61. The middle three rungs held inside six per cent, so the drift is not uniform: it lives at the ends of the ladder, which is where the ladder was most interesting.

Two further things are wrong with the ratio beyond its instability. Nobody deploys bare node:http with hand-rolled routing, so the denominator is a reference the reader cannot obtain and has no feel for. And the generator's own floor does not cancel the way README.md claims. A floor F added to both sides gives (Tf + F) / (Tb + F), not Tf / Tb. With a 150 µs floor, a framework genuinely costing twice the baseline's 50 µs reports 1.25 instead of 2.00. Cancellation holds for a difference and fails for a quotient, so every low-load ratio understates overhead, and understates it most where frameworks differ most.

Fix the machine and none of this needs a workaround. Absolute milliseconds are reproducible, they are what a reader can hold against their own traffic and their own SLO, and they are a denominator every language shares — which puts Go against Node on the same axis for the first time, something README.md currently rules out in as many words.

§2 · The machine

One box, fixed clock, real cores

Reproducibility is the precondition for everything else here. It is bought with configuration, not with statistics.

An AMD 5700G in a Supermicro 2U chassis. Eight Zen 3 cores on a single CCX sharing 16 MB of L3, so every core is equivalent and no cpuset assignment has to think about crossing a chiplet. A 65 W part with that much air in front of it does not throttle, which removes thermal drift as a design concern rather than as an assumption to be checked each run.

Cores 0–1 carry the target, 2–3 the generator, and 4–7 are left to the kernel and Docker. RB_CPUS stays 2, and it stops being an implementation detail: two-core numbers do not transfer to a four-core task, so the container's CPU budget is part of every published result.

The self-hosted runner must not touch pull requests

The repository is public and validate.yml triggers on pull_request, so a fork's code would execute on this machine. measure.yml triggers only on schedule and workflow_dispatch, both of which run from this repository's own ref, and it is the only workflow that moves. validate.yml and deps.yml stay on GitHub-hosted runners, which also keeps DEPS_TOKEN off the box. The runner runs as a non-root user with no credentials beyond its registration token.

§3 · Two rates

Chosen from the traffic side, identical for every language

Five rungs become two, and the numbers stop being divided by anything.

Two fixed offered rates, the same for every target in every language. A regular rate everything is expected to complete, and a raised rate that separates the frameworks with headroom from the ones without. The published statistic is p50 and p99 in real time at each.

The rates come from what a reader might want to serve, not from where the targets break. That distinction decides whether the constant is stable. Set from the population, the rate wants to move every time a language is added and moving it breaks the time series; set from the traffic side it is a spec constant changed rarely and deliberately, with a marked discontinuity when it is. 1,000 and 5,000 rps on two cores is the starting pair, and it is a guess until the hardware runs. The live values are in spec/ladder.json, which is the only place they are authoritative.

One rate for every language, not one per language. A per-language raised rate is a relative measurement with an absolute label on it: it grades slow languages on a curve, which is the thing this design exists to stop doing. A customer does not care what language the backend is written in and no host discounts a language, only a CPU. If a language cannot serve 5,000 rps on two cores, that is the result.

The consequence is that the raised rate may be empty for a whole language. That is a finding, not a gap, and §4 is how it renders. If a rate turns out to be so high that it is uninformative for an entire language, the answer is a third global rate rather than a per-language one — same constant for everyone, and the reader picks the row matching their traffic.

Four minutes at the regular rate is below the spec's own floor

1,000 rps for 240 s is 240,000 requests over 48 endpoints drawn uniformly, 5,000 each. The blend number is unaffected, since it aggregates all 240,000. The per-endpoint drill-down the site renders is: 5,000 samples puts a p99 on roughly 50 observations. The three ways out were a higher regular rate, a 7.5-minute sample, or bringing the constant down to what the run delivers. #38 took the third: min_requests_per_endpoint is 4,000, because the first two move every published latency and this one only stops the file claiming something untrue. The raised rate has no such problem.

§4 · Failure

A target that cannot keep up gets a count, not a latency

No blend is computed at a rate the target did not complete, because the percentile would flatter it.

gen/blend.mjs drops by never sending. When the in-flight count reaches maxInflight the scheduler increments dropped and moves on, so a dropped request never enters a histogram:

if (inflight >= maxInflight) { dropped++; issued++; continue; }
fire((rnd() * eps.length) | 0, dueNs);

The percentiles at a saturated rate are therefore computed over survivors, and the requests excluded are exactly the ones that would have been slowest. A framework that collapses drops more and reports a better p99 than one that degrades gracefully. That inversion is the reason for the rule rather than a detail of it.

So: a blend is computed only where the target completed the rate. Above the drop threshold there is no blend number at all, and the row instead carries what actually happened.

The row is flagged in the failure colour and carries its drop count, so it reads as a failure rather than as missing data. Those are opposite meanings and an empty cell renders them identically. Achieved rps is the honest headline at the raised rate: gen/blend.mjs already computes it as done / elapsed and run.py already records it, so nothing new has to be measured.

Abort a failing rate early. A target dropping thirty per cent twenty seconds in will drop thirty per cent four minutes in. Record the failure and move to the next target. Across the slow half of the population that is close to an hour at full build-out, and it is what makes a third rate affordable later.

summarize.py already carries SATURATION = 0.01 from the ratio design. The threshold survives; what it gates changes from a marker on a published number to whether a number is published.

§5 · The run

One host a night, about eight hours

Losing the six-hour hosted cap is what pays for the longer samples.

PhaseDurationNote
boot + conformance~60 sOn a boot of its own, stopped once it passes. Longer for a JVM target. The 45-endpoint fingerprint pass is unchanged.
measured bootsecondsThe same image started again and timed, from docker run to the first 200 on /health. A JVM target is the slow end.
warmup90 sOnce per target, at the regular rate. JIT class sets the floor and everything shares it. Recorded as the ramp.
regular rate240 sRecorded.
settle15 sDiscarded. The connection pool and GC adjust to the new rate; the first seconds would measure that.
raised rate240 sRecorded, or aborted early on drops.
teardown + cooldown~25 srun.py waits for the port and sleeps 0.5 s today; on a persistent box the gap can be longer for free.

The measured boot and the warmup are published. The boot is timed by two clocks. The target reports boot_ms on /__meta, from the start of its process to listening. The harness times docker run and then the wait for the first 200, and keeps both halves and their sum. It also times the probe that got that 200, which is the first request the target served. Some runtimes do real work on their first request, and this is where it shows. The warmup is kept as a ramp: the first request, sent alone, then the latency distribution of each slice of the schedule, one second wide for the first ten seconds and ten seconds wide after. Conformance has a boot of its own, because on the measured boot it would spend the first request before anything recorded it. That earlier boot also leaves the image in the page cache, so what is published is a warm-page-cache cold start. That models a scale-out onto a node that already has the image, not a first deploy. Only a container run's boot is published, because --mode local compiles Go and Rust on first launch. Each target row carries its position in the run, because a target late in the order boots on a machine that has been under load for an hour.

About eleven minutes a target. Nineteen implemented targets is three and a half hours. The full forty-three is close to eight, which is one host for one night.

That is the scheduling constraint, and it is forced by having one machine rather than chosen. The container host is the expensive one because its suite runs for a fixed duration. The function hosts run the serial suite, which is bounded by a request count instead, so they cost a fraction of a container run and can plausibly share a night — worth timing one serial target before committing to a rotation. The thing that does not fit is splitting the container host into HTTP/1.1 and HTTP/2, which doubles the expensive host to sixteen hours. HTTP/2 also needs a transport gen/blend.mjs does not have, since it is node:http today, so it is its own change on its own night.

Averaging the last three runs was proposed when every run was a different machine. On fixed hardware it is a smoothing convenience rather than a correction, and with one host a night it would put the tail of the window fifteen nights back. Decide it against the observed run-to-run spread once the box has a week of history; if the spread is small, publish the run.

§6 · Knowing a run went wrong

The population is the control

Forty targets whose code did not change is a better detector than a baseline booted twice.

Most targets in any run are unchanged from the night before. If frameworks that did not change move together, the run is suspect. That has more power than two boots of one baseline, it catches per-target problems a baseline cannot see, and a uniform shift still shows as forty time series moving together, which is a stronger signal than one moving.

What it cannot do is attribute: it says the run is anomalous, not what changed. The known confound is deps.yml, which opens version bumps nightly, so the set of unchanged frameworks shrinks on exactly the nights it is most needed, and a runtime bump moves several targets of one language together in a way that resembles machine drift.

One hole there is worth closing whatever else is decided. bundle_hashes covers the Dockerfiles, so a change to the base image tag is caught, but node:24 is a moving tag and the digest under it changes with no file changing. Every hash can be identical while the runtime underneath is different. Recording the resolved image digest per target per run closes it, and it is a docker inspect after the build.

The per-language baselines were removed rather than kept as rows. They were hand-rolled segment dispatch, which is a second implementation to maintain, to answer questions about, and to keep conforming, and nothing is divided by them any more. Each language now names an anchor in spec/matrix.json — Fastify, Gin, Spring Boot — which boots first and holds the one job the baseline still had: being the response fingerprint the rest of the language is gated against.

§7 · What publishing a real number obliges

The floor is now inside the result

A ratio partly hid the driver. An absolute does not.

At 500 rps the generator's floor measured 150–200 µs against target p50s of the same size. Published as an absolute, a 0.4 ms result would be wrong by a third. The floor has to be measured against a null target and either subtracted or driven under the noise. Most of it is the C-state exit from §2: baseline p50 by rung ran 315, 146, 134, 124, 384 µs, and a target does not get faster as load rises. The monotonic fall from 500 to 6,000 rps is the idle path, not the framework.

The driver must also not be the bottleneck at the raised rate. Its own capacity on two pinned cores needs measuring before 5,000 is fixed as a constant, and the same measurement gives the floor.

Then the machine becomes part of the result and travels with it: CPU, core count, the two-core container budget, fixed clock with boost off, kernel and Docker versions. site/ currently tells the reader that runs happen on GitHub-hosted runners whose CPU varies between runs, which is the note this replaces. Worth stating too that the latency is target plus loopback and excludes the load balancer a reader will have in front of it.

The cost of the reversal, so it is a decision and not a surprise: absolute numbers are stranded if the machine dies, where ratios were not. A replacement box has to be characterised against the one it replaces by running the same target images on both, which means keeping the old one alive long enough to do it. And the numbers are true for a two-core container on Zen 3 at a fixed clock; they say nothing about Graviton or about an eight-core task. That is a scope statement to publish, not a flaw to hide.

§8 · Order of work

Hardware first, because it sets the constants

The rates cannot be chosen from a laptop.

  1. Build the box and pin it

    SMT off, boost off, governor performance, max_cstate=1, isolcpus on 0–3, native Docker. Register the runner against measure.yml only.

  2. Characterise the generator

    Null target, sweep the rate. Produces the floor to subtract and the ceiling the raised rate must stay under. Both are inputs to every number after this.

  3. Fix the two rates

    Start at 1,000 and 5,000, run the implemented targets, and see what completes. Write the result into spec/ladder.json, which becomes the source of truth.

  4. Collapse the ladder

    run.py loses three rungs and gains the settle gap and the early abort. summarize.py stops dividing and gates the blend on completion instead of flagging saturation.

  5. Record the digest

    docker inspect after build, carried on the target row beside bundle_hash.

  6. Rebuild the display

    Two permanent rate columns in place of the rung dropdown, real times as the headline, achieved rps and drop count on the raised rate, failure colour on a row that did not complete.

  7. Rewrite the two rules

    README.md opens with "Nothing absolute is ever published." That inverts. The second rule, that behaviour is shared and wiring is not, is untouched and does the same job it always did.
